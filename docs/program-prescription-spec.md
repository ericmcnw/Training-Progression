# Program / Prescription Layer — Spec

**Written 2026-08-06.** The missing primitive that turns the app from a *tracker*
into a *training platform* — and the prerequisite for coaching other people.

---

## The gap

**The app records what you did. It has no concept of what you were supposed to do.**

Today a `Routine` holds exercises + `defaultSets` — no target reps, no target
load, no tempo, no progression. So the prescription ("3×10 @ 80 lb, 3s eccentric,
hold load if the morning reading is up") lives in a chat window, not the app.

Survivable solo — you keep the plan in your head. **Fatal for coaching**, because
coaching *is* prescription.

Symptom to point at: Eric asked "what's the plan for today?" nearly every day for
two weeks, and two weeks of walks went unlogged, because the plan had no home.

## Why Focus feels "off" (diagnosed 2026-08-06)

`Focus` describes **intent** but drives nothing. A milestone says "progress
hangboard load" — not to what, by how much, or on which days. The schedule is
built separately and doesn't know the roadmap exists. Meeting a gate just flips a
chip green.

Five concepts currently compete to answer "what should I do and when":
Routines · Schedule · Rotation · Goals · Focus. **None of them is a training
plan**, and they don't nest. That's the crowded-but-incomplete feeling.

---

## Resolution: a hierarchy

| Layer | Concept | Answers | Status |
|---|---|---|---|
| Strategic | **Focus** | *why* — the season's objective | exists |
| Structural | **Program** | *what + how* — weeks, sessions, prescribed work | **NEW** |
| Temporal | **Schedule** | *when* — generated by the program | exists |
| Template | **Routine** | the session shape | exists (gains default prescriptions) |
| Record | **Log** | what actually happened | exists |
| Measure | **Goal** | did it work | exists |

**Consolidation candidate:** `Rotation` becomes a *mode* of Program
(flexible / log-advanced) rather than its own top-level concept. Kills one of the
five competing primitives.

## Focus × Program — gating, not replacement

They answer different questions and are complementary:

- **Focus / ProgressionMilestone = READINESS.** Criteria-gated, not date-locked.
  *"Advance when pain ≤2 for three days."*
- **Program = CONTENT.** Time-structured prescription. *"This block is 3×10 @ 85,
  twice a week."*

**Connect them so a met gate UNLOCKS the next block** — that's what makes Focus
stop being observational:

```
Focus: "Snowboard-ready by December"
 ├─ Milestone: restart loading   gate: pain ≤2 ×3d              → unlocks Program "Base Block" (4wk)
 ├─ Milestone: curls climbing    gate: load ↑ ×3 sessions       → unlocks "Build Block"
 └─ Milestone: reintroduce plyo  gate: distal ≤2 + curls ↑      → unlocks "Power Block"
```

Schema cost: one field — `Program.gatedByMilestoneId`.

This mirrors real staged rehab: criteria-gated phases *plus* a weekly program.
Neither replaces the other.

## Data model

Prescription lives at **two levels** — that's what makes it work:
- **Routine** holds a *default* prescription → logging without a program still shows targets.
- **Program** *overrides* per week → that's how progression happens.

```
Program            name, description, status(draft|active|archived),
                   focusId?, gatedByMilestoneId?, mode(structured|flexible)
  └ ProgramWeek    weekNumber, label ("Base wk 1"), notes
     └ ProgramDay  dayIndex 0-6, label ("Lower A")
        └ ProgramItem   routineId | activityTypeId | sportSlug,
                        sortOrder, notes, gateNote
           └ Prescription   exerciseId, sets, repsMin, repsMax, seconds,
                            load, loadUnit(lb|pct1rm|rpe|stack),
                            tempo, restSec, cue

Prescription also attaches optionally to RoutineExercise (the default layer).

ProgramInstance    programId, startYmd, status
                   ← activating a program generates existing
                     ScheduleManualEntry rows. Programs sit ABOVE the
                     schedule; they don't replace it.
```

### Progression: author it, don't automate it (at first)
Explicit weeks (copy week 1, edit numbers) beats rule-based ("+2.5 lb/wk") for v1.
It's what coaches actually do, it handles deloads / gates / "hold if the reading is
up," and it's a fraction of the build. Add rules later for boring linear stuff.

## UI — prescription without crowding

The prescription mostly costs **zero space** if placed right:

1. **Target as placeholder text in the set inputs** — reps field shows a greyed
   `10`, weight field a greyed `80`. Target is visible *inside* fields already
   being rendered. Tap to accept, type to override. **Zero added chrome.** ← best idea
2. **One dense target line under the exercise name** — `3×10 @ 80 lb · 3s ecc`.
   Muted, single line, never a paragraph.
3. **Cues behind a tap, and only when they exist** — a small ⓘ that expands the
   coaching note inline. **No note → no icon.** Chrome appears only when there's
   something to say.
4. **Session-level instructions in ONE collapsed banner at the top** — gate notes,
   coach comments, "hold load if the morning reading is up." Use the existing
   `CollapsibleSection`. All prose lives here so it never sprinkles across rows.
5. **Reuse the `InlinePainCheck` pattern** — a collapsed `<details>` in every log
   form that costs nothing when ignored. Same shape already solved this problem.

Net: an unprescribed session looks exactly like today. A prescribed one gains a
muted target line, pre-filled placeholders, and one collapsed banner.

## Build order

1. **Prescriptions on `RoutineExercise` + shown in the log form** — small,
   immediately useful solo. *This alone fixes the daily "what's the plan" problem.*
2. **Program container + week/day authoring UI** (the builder)
3. **Activate → generate schedule** (bridge to `ScheduleManualEntry`)
4. **Adherence view** — prescribed vs actual, per session and per week
5. **Focus↔Program gating** — `gatedByMilestoneId`, block unlocks on met gate
6. *(post-auth)* **Assignment + coach roster + compliance dashboard + feedback**

Steps 1–5 are fully valuable with **zero other users**. Step 6 is the only
genuinely coaching-specific work, and it's small once 1–5 exist.

## Coaching additions (post-auth, step 6)

- `ProgramAssignment` (programId, athleteId, startYmd, status) — one program,
  many athletes
- Coach roster view + per-athlete compliance dashboard
- Comments/feedback on individual logs (distinct from prescription cues)
- Program templates / duplication

**Prerequisite:** auth/multi-user. Core training models (`RoutineLog`, `Routine`,
`PainLog`, `Focus`…) currently have **no `userId`/`profileKey`** — see
`docs/auth-migration-hit-list.md`. New program models should carry an owner
column from day one so they don't join the backlog.
